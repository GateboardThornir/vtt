# 010 — User entity + password hashing

**Status:** in review
**Depends on:** 006 (Phase 0 complete)
**Branch:** `task/010-user-entity-and-password-hashing`

## Goal

The first domain table: an account with a username, a correctly hashed password, and a lifecycle
state. Every Phase 1 task about accounts builds on this shape, and the hashing decision made here is
the one that protects every password the platform ever stores.

## Scope

In scope:
- The `Accounts/` module folder — the first one, establishing the pattern `.claude/rules/backend.md`
  describes
- A `User` entity: identifier, username, password hash, account state, creation timestamp.
  **No email field, and no field that could become one**
- Account states `Pending`, `Active`, `Disabled`, per the roadmap
- `UserConfiguration : IEntityTypeConfiguration<User>`, discovered by the assembly scan already
  present in `VttDbContext` — task 003 built that scan precisely so this task adds a table without
  editing the context
- Case-insensitive uniqueness of usernames, **enforced by the database**
- A password hashing service wrapping the framework's hasher, exposing hash and verify, and
  surfacing the "this hash used an outdated work factor" signal even though nothing consumes it
  until task 013
- The first real migration, which is also the first exercise of the snake_case convention from
  ADR 004
- Test isolation: resetting the database between integration tests, deferred here from task 005
- Unit tests for hashing behaviour; integration tests for persistence, the state round-trip and the
  uniqueness constraint

Explicitly out of scope (and which task covers it instead):
- **Every HTTP endpoint.** No controller, no DTO, no request validation. Registration is 012, login
  is 013. This card produces a table and a service, nothing a browser can reach
- Invite tokens and their consumption — 011
- The admin approval queue that moves `Pending` to `Active` — 014
- Recovery codes — 015
- Cookie sessions and anything that authenticates — 013
- Platform role (admin versus member) storage and policies — 016. See the open question below
- Any UI — 017
- Campaign membership and campaign roles — 021, and they are a different concept entirely

## Open questions to settle before implementation

**1. Does `User` get a platform-role column now, or at task 016?**

The roadmap gives 010 only the three account states and gives 016 "platform role (admin/member) +
campaign role resolution helper". Task 014's approval queue needs to know who the admin is, so the
storage has to exist by then.

Recommendation: **leave it out of 010** and let 016 add the column. Migrations are append-only and
adding a nullable-or-defaulted column is routine, so deferring costs one small migration and keeps
this card exactly as wide as the roadmap drew it. The alternative — adding a role column now that
nothing reads for six tasks — is the speculative work the scope rules forbid.

**2. Where does the first administrator come from?**

Registration requires an invite; invites are generated by an admin (011). Nothing in the plan
creates the first admin, so the system as specified cannot be bootstrapped. This is a real gap in
the roadmap rather than a detail of this card.

It needs an owner — most plausibly 011 or 014 — and a mechanism: a seeded account, a one-off
command, or a first-user-becomes-admin rule. **Not to be solved inside 010**, but it should not be
discovered later either.

## Approach

**ASP.NET Core Identity is not adopted; only its password hasher is.** Identity's EF schema ships
`NormalizedEmail`, `EmailConfirmed`, `PhoneNumber` and `TwoFactorEnabled` columns, which collide
head-on with the rule that no email field exists anywhere in the schema. Its flows assume email
confirmation and email-based reset, both of which this platform deliberately does not have. Taking
Identity and stripping it is more work, and more ongoing friction, than not taking it.

What is worth taking is `PasswordHasher<TUser>` from `Microsoft.Extensions.Identity.Core`: it is the
framework's current recommended algorithm and work factor, which is exactly what
`.claude/rules/security.md` asks for, and it is maintained by people who will raise the work factor
when hardware moves. Writing a hasher by hand would be the single worst decision available here.
This warrants an ADR.

**Uniqueness is a database constraint, not a service check.** "Look for the username, then insert if
absent" has a race between the two statements, and under concurrent registration it produces
duplicate accounts. A unique index is the only thing that actually holds. Because usernames must be
case-insensitive — `Mattia` and `mattia` are the same person — that means a unique index on the
lowercased username, and the implementation must decide between a functional index, a stored
normalised column, and the `citext` extension.

**States are stored readably.** The point of ADR 004's snake_case was that the database is read by
hand; a `state` column containing `1` undoes that. Persist the enum as text, and accept that
renaming a state later becomes a data migration.

**Test isolation arrives with the first table.** Until now the integration tests wrote nothing, so
the container's contents did not matter. Once tests insert users, one test's rows are the next
test's surprise. Task 005 deferred this here for exactly this reason.

## Acceptance criteria

- [ ] A migration creates the table, and `psql` shows snake_case names throughout — table, columns,
      and the unique index
- [ ] The migration's `Up` is reviewed and understood before it is committed, not merely generated
- [ ] Inserting two users whose usernames differ only in case fails, and fails at the **database**
- [ ] A hashed password does not contain the password; the same password hashed twice produces
      different hashes; verification succeeds for the right password and fails for the wrong one
- [ ] The account state round-trips through the database and reads as text in `psql`
- [ ] Integration tests are independent: running the suite twice in a row passes both times, and
      tests pass regardless of the order they run in
- [ ] No occurrence of the word "email" anywhere in the added code, schema or tests
- [ ] The migration-parity test from 003 is now meaningful — verify it fails if the entity changes
      without a migration
- [ ] `dotnet build` zero warnings, `dotnet format` clean, full suite green, CI green

## Concepts to explain

- **Why passwords are hashed and not encrypted**, and why that distinction is the whole ballgame:
  encryption implies a key that can decrypt, and there is no legitimate reason to ever recover a
  password
- **Salt, work factor, and what "slow on purpose" means.** Why a fast hash like SHA-256 is the wrong
  tool, what a rainbow table is, and how a per-password salt defeats it
- **PBKDF2 versus bcrypt, scrypt and Argon2** — what the framework actually uses, and why "whatever
  the framework currently recommends" is a better policy for a solo maintainer than picking a
  favourite algorithm
- **Rehashing on successful verification**: how a work factor gets raised over the life of a system
  without anyone resetting their password
- **Why ASP.NET Core Identity was declined**, and what is lost by declining it — this is the largest
  build-versus-adopt decision in Phase 1
- **`IEntityTypeConfiguration` and the assembly scan**: how a table gets added without touching
  `VttDbContext`, and why that matters for module boundaries
- **EF value converters**, and what storing an enum as text costs and buys
- **Expression indexes in Postgres**, and why case-insensitive uniqueness is harder than it looks
- **Why uniqueness cannot be enforced in application code** — the check-then-act race, and how the
  database is the only place with the atomicity to settle it
- **Test isolation strategies**: truncate-between-tests versus transaction-rollback versus a fresh
  database per test, and what each costs

## Risks and things to watch

- **The hash must never be logged, returned, or serialised.** It leaves the database only to be
  verified against. Worth an explicit test asserting it does not appear where it should not, once
  there is an endpoint to test — a note for 012, not work for here.
- **Case-insensitive uniqueness has a subtlety beyond casing**: Unicode. Two usernames can look
  identical and differ in code points. Out of scope to solve, but worth knowing it exists before
  someone reports it as a bug.
- **Storing the enum as text makes a rename a data migration.** Choose the three names as though
  they are permanent, because effectively they are.
- **The first migration sets the pattern every later one copies.** Read it fully. If snake_case is
  wrong here, it is wrong in twenty migrations' time.
- **Do not add a "roles" or "permissions" concept.** Campaign roles are 021 and are not the same
  thing as the platform role; conflating them early is how an authorisation model becomes
  unfixable.
- Resist adding registration "since the entity is right there". A card that produces a table and a
  service is complete when the table and the service exist.
