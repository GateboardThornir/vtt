# Tabletop RPG Platform — Functional Specification

**Status:** Baseline v1.0 — consolidates all decisions from the requirements-analysis and architecture interviews (July 2026).
**Purpose:** This is the foundational document for the project. It records what the platform is, what it must do, and the constraints under which it will be built. Architectural detail beyond the summary in §10 lives in a separate architecture document.

---

## 1. Vision and product summary

A private, invitation-only web platform for playing tabletop role-playing games live over the internet. It is a full **virtual tabletop (VTT)**: groups gather in real time around a shared digital game table with battlemaps, tokens, fog of war, dice, character sheets, voice and video — with the platform itself understanding and automating the rules of the game system in play.

The platform is **multi-system by design**. Dungeons & Dragons 5th Edition is the first supported system, built on the freely licensed SRD content, but the core makes no assumptions about any particular game: rules knowledge is packaged into interchangeable *system modules* authored and shipped by the platform maintainer.

The intended audience is a closed circle of trusted users — a friend group of fewer than fifty people — with membership controlled by an administrator. This is not a public product and is not designed to scale beyond that community.

## 2. Scope

**In scope:** account management with admin approval; campaign and session management with scheduling and RSVP; a live, server-authoritative game table with maps, tokens, fog of war, initiative tracking, dice, and per-system rules automation; structured character sheets with derived-stat calculation; compendiums (bundled SRD plus Master-uploaded content); shared materials with per-player visibility control; built-in text chat, peer-to-peer voice/video, and GM-controlled synchronized ambient audio; hosting of maps, tokens, images, PDF handouts, and audio files; a bilingual (Italian/English) interface.

**Out of scope:** public registration or discovery; asynchronous play-by-post; an in-app builder that lets users author new game systems; redistribution of copyrighted (non-SRD) rulebook content; playing the live table on smartphones; session recording; video-clip hosting; email-based flows of any kind (no email addresses are collected).

## 3. Users, roles, and access

There are two account-level distinctions and one campaign-level role.

**Administrator.** A platform-level account that approves or rejects registrations, manages user accounts, and performs account recovery. The admin does not have privileged access to campaign content by virtue of being admin.

**Member.** Every approved user. Membership itself carries no gameplay role: **any member may create a campaign, and creating a campaign makes them its Master (Game Master)**. The same person can therefore be the Master of one campaign and a Player in another. Master and Player are roles *within a campaign*, not account types.

**Master (per campaign).** Full control over their campaign: roster, sessions, scenes and maps, all content and its visibility, all characters, and the live table. The Master has a private "behind the scenes" preparation space, invisible to Players until material is deliberately revealed.

**Player (per campaign).** Joins a campaign roster by invitation from its Master, manages their own character sheet (under Master oversight), views materials the Master has made visible to them, participates in sessions, and interacts with the table within the permissions the Master and the active game system grant.

### 3.1 Registration and account lifecycle

Registration is possible only through a dedicated invitation URL (a single-use token generated by the admin). The applicant chooses a username and password — **no email address is requested or stored** — and the account enters a *pending* state until the admin explicitly approves or rejects it. Only approved accounts can sign in.

### 3.2 Account recovery

Because no email exists, recovery is admin-mediated: the admin generates a **one-time reset code**, delivers it to the user out-of-band (in person, messaging apps), and the user consumes it to set a new password. The admin never sees, sets, or knows a user's password at any point. Lost usernames are resolved the same way, by the admin looking up the account.

### 3.3 Notifications

All notifications (campaign invitations, session scheduling, RSVP requests, approval outcomes) are **in-app only**, as a direct consequence of collecting no email addresses.

## 4. Campaigns and sessions

A **campaign** is the long-lived unit of play: it has one Master, a Player roster, a pinned game system (and system version — see §8), a persistent world state, its content library, and its session history. Campaign state persists indefinitely across sessions; nothing resets between play dates.

A **session** is a scheduled live event within a campaign. Sessions inherit the campaign roster automatically — Players are not re-invited each time — and each scheduled session carries a **per-session RSVP**, so the Master knows who will attend. Sessions are **live and synchronous only**: the table is active while a session runs, and there is no asynchronous play mode.

The Master's preparation space belongs to the campaign, not the session: scenes, maps, encounters, and materials can be staged in advance at any time and revealed during play.

## 5. The live game table

The table is the real-time heart of the platform. During an active session, all participants share a synchronized view governed by these functional rules:

**Battlemap and tokens.** The Master presents scenes built on uploaded map images, with movable tokens representing characters, monsters, and objects. Players can move tokens they own; the Master can move anything.

**Fog of war.** The Master controls which areas of the map each Player can see. Hidden regions, hidden tokens, and unstaged prep **must never be transmitted to Player clients** — visibility is a server-enforced security property, not a client-side display choice (see §9).

**Initiative and turns.** Combat uses an **advisory initiative tracker**: the table displays turn order prominently, but does not mechanically lock other participants out of acting. Order is a shared social convention supported by the software, not enforced by it.

**Dice.** A dice roller integrated with chat and with character sheets, supporting the dice semantics of the active game system, with public rolls, private rolls, and Master-only rolls.

**Rules automation.** The table understands the active system's rules to the depth the system module implements: resolving attacks, applying damage and conditions, tracking resources such as spell slots, and computing derived values. Automation is authoritative — the server validates every action against the rules — but the Master retains override authority for rulings.

## 6. Communication and shared media

**Text chat** is built in, scoped to the table, with dice-roll integration and support for in-character/out-of-character distinction.

**Voice and video** are built in, per table, implemented as a **peer-to-peer WebRTC mesh** among the participants (audio always, camera optional). Media never transits the platform server except when a participant's network blocks direct connection, in which case a TURN relay on the server carries that participant's stream. There is **no recording**.

**Synchronized ambient audio.** The Master uploads music and ambience tracks to the campaign library and controls playback for the whole table (play, pause, seek, volume). Synchronization is command-based: clients fetch the audio file themselves and obey the Master's playback commands, keeping all participants in step.

## 7. Content model

### 7.1 Characters

Character sheets are **structured, per-system, and calculated**: their shape is defined by the active system module, derived values (modifiers, saves, capacities) are computed automatically, and the sheet participates fully in rules automation. Sheets are **campaign-scoped** — they live inside a campaign under full Master oversight — but every Player can **export their character** in a portable format at any time, so a character is never held hostage by a campaign's lifecycle.

### 7.2 Compendiums

Compendium content (spells, monsters, items, rules entries) comes from two sources. The platform **bundles the D&D 5e SRD**, imported once through an offline ingestion pipeline. Masters may additionally **upload their own content** into their campaigns: entries that conform to the active system's schemas participate in automation exactly like bundled content, while free-form material is supported as handouts (below) without automation.

### 7.3 Shared materials and visibility

Masters share documents, images, and handouts with their campaign. Visibility follows a **campaign-wide default with per-item, per-player exceptions**: a handout is normally visible to the whole roster, but the Master can restrict any individual item to specific Players (secrets, private letters, faction knowledge). As with fog of war, restricted items are filtered server-side and never reach unauthorized clients.

### 7.4 Hosted asset types

The platform hosts **maps, tokens, images, PDF/document handouts, and audio files**, under per-campaign storage quotas. Video files are not supported.

## 8. Game system model

A game system is a **versioned platform artifact**, authored and shipped by the platform maintainer — never user-created. Each system module packages three things:

1. **Declarative schemas** (JSON) defining the shape of character sheets and compendium entries for that system;
2. **Automation code** implementing the system's rules as handlers for player and Master actions, plus derived-stat calculators and dice semantics;
3. **A version identifier**, with explicit migration logic between versions.

Every campaign **pins the system version** it was created with. Upgrading a campaign to a newer system version is a deliberate, migrated operation — never implicit — so that long-running campaigns and their characters survive the evolution of the system modules. This versioning discipline is a foundational rule of the project.

The first shipped system is **D&D 5e (SRD-based)**. The platform core contains no knowledge of any specific game's rules.

## 9. Content licensing policy

The platform bundles and redistributes **only** content it is legally entitled to: for D&D 5e, the System Reference Document released under Creative Commons. Copyrighted rulebook material (e.g., full Player's Handbook content, non-SRD monsters) is **never shipped, bundled, or redistributed by the platform**, regardless of the platform being private. Masters uploading material into their own private campaigns do so under their own responsibility; the platform's obligation is to keep such uploads confined to the campaign they belong to.

## 10. Non-functional requirements

**Scale.** Under 50 total users; a handful of concurrent live tables of 4–6 participants each. All design decisions are sized to this reality, not to hypothetical growth.

**Devices.** The *around-the-game* surfaces (campaign pages, character sheets, handouts, chat, scheduling) are responsive down to tablet. The **live table requires tablet or better for Players and desktop for the Master**. Smartphones are explicitly unsupported for the live table.

**Languages.** The interface is available in **Italian and English**, with internationalization infrastructure in place from the first release. Bundled SRD content remains in English.

**Security.** Server-authoritative everywhere: clients express intents, the server validates and decides. Visibility filtering (fog of war, hidden prep, per-player secrets) is enforced at the server boundary — no data a user is not entitled to see ever reaches their client. Authentication uses username/password with server-side sessions; invitation tokens are single-use; admin recovery codes are one-time.

**Data safety and availability.** Operational bar is deliberately modest: best-effort availability with no formal SLA. The requirement that actually matters is stated plainly: **the platform must be stable during scheduled play sessions, and a campaign accumulating years of play must not be lost.** Accordingly, despite the best-effort stance, a nightly automated database dump and asset sync to off-site object storage is adopted as a standing measure (maintainer's recommendation, accepted), and the table engine's event log provides crash recovery for live sessions.

**Advertising, tracking, external services.** None. The platform is self-contained except for the off-site backup target and the WebRTC TURN fallback.

## 11. Constraints

The platform is built and maintained by a **single developer**, confident in C#, TypeScript/JavaScript, SQL, and Python. Production infrastructure is a **single 4 GB VPS (Hostinger, ~€10/month)**; the only workload excluded from it by design is live media, which flows peer-to-peer. Monthly running costs must remain in this order of magnitude.

## 12. Delivery strategy

Delivery follows **staged internal rollouts**: the maintainer's own group plays on the platform from the first usable milestone, acting as testers; the "official release" to the wider community happens when the full vision is complete. Real play between phases is a deliberate design input, especially for rules automation.

- **Phase 1 — first playable.** Accounts, admin approval, campaigns and rosters, 5e character sheets with derived stats, chat and dice, static maps with tokens and Master-hidden layers. Voice via external tools (Discord) temporarily.
- **Phase 2 — the real table.** Fog of war, initiative tracker, the intent/validation pipeline with first 5e automation (attacks, damage, conditions), handouts with per-player secrets, session scheduling with RSVP.
- **Phase 3 — full vision.** Built-in voice/video (P2P mesh), synchronized ambient audio, deeper 5e automation, character export, i18n completion and polish. Official release closes this phase.

## 13. Architectural decisions (summary)

Recorded here for traceability; the architecture document is authoritative for detail.

| Area | Decision |
|---|---|
| Backend | ASP.NET Core (C#) modular monolith; SignalR for real-time sync and WebRTC signaling |
| Frontend | TypeScript + React; PixiJS (WebGL) for the battlemap canvas |
| Database | PostgreSQL — relational core plus JSONB for system-defined content |
| Real-time model | Server-authoritative in-memory table state; intent → validate → broadcast; event log + snapshots for persistence and crash recovery |
| Game systems | Hybrid packaging: JSON schemas + C# rule modules behind a platform interface; campaigns pin system versions |
| Media | P2P WebRTC mesh; coturn on the VPS as STUN/TURN fallback; command-based audio sync |
| Deployment | Docker Compose on the VPS (app, PostgreSQL, coturn, Caddy for TLS); GitHub Actions CI; nightly dumps and asset sync to object storage (Cloudflare R2 / Backblaze B2) |
| Tooling | Python for offline pipelines, notably SRD ingestion |

## 14. Open points and accepted risks

- **Feasibility risk (accepted, mitigated):** the full-VTT scope is very large for a solo developer; the staged-rollout strategy with real play between phases is the adopted mitigation.
- **TURN bandwidth:** relay traffic through the VPS when P2P fails counts against Hostinger's bandwidth allowance; to be verified against the plan's limits.
- **Storage growth:** audio and map assets will dominate disk usage; per-campaign quotas are required from Phase 1, exact figures to be set.
- **System-version migrations:** migration tooling between 5e module versions is mandatory before any breaking schema change ships — no exceptions.
- **Detailed module design:** table engine and system contract are the next design targets; ERD and API surface follow from their interfaces.
